1. Executive Overview

OpenSooq CDC Data Analyzer is a client-side web application that turns Change Data Capture (CDC) exports — typically dense database dumps in CSV or PDF form — into human-readable business intelligence about OpenSooq listings.

Operations, moderation, and engineering teams often receive CDC snapshots that contain opaque field names (SF_OP, SF_OFFSET_ID, LAST_EDIT_ACTION), numeric status codes, and rule-engine JSON. This product maps that raw stream into:

  • A dashboard of activity, status, and risk signals
  • Searchable, filterable record tables with human or raw labels
  • Full listing lifecycle timelines (first event → last event, with gaps and evidence)
  • Status history tracking across official OpenSooq status codes (100–301)
  • Smart insights and QA anomaly detection
  • Side-by-side record comparison and multi-format export
Privacy by design All parsing and analysis run locally in the user’s browser. Uploaded files are never sent to a backend or third-party AI service by default.

2. Goals & Value Proposition

2.1 Problems solved

ProblemHow the analyzer helps
CDC dumps are hard to read Field dictionary maps technical names to business labels and descriptions
Status codes are numeric and inconsistent across sources Official codes 100–301 plus aliases (including Arabic-aware normalization)

Anomalies are easy to miss QA engine flags multi-status churn, post-delete updates, missing prices, etc.

2.2 Primary users

Operations & Moderation

Investigate listing status journeys, violations, and rule-engine actions without SQL.

Engineering & QA

Validate CDC exports, spot ordering issues, compare records, and export evidence packs.

3. System Architecture

The application is a single-page Next.js client. There is no application backend for file processing. The browser loads the UI, the user selects a file, and the analysis pipeline runs entirely in memory via Zustand state.

3.1 High-level flow

Upload PDF/CSV → Read file → Parse (Papa Parse / PDF.js) → Normalize rows → Analyze (insights + lifecycle + status) → Dashboard & views

3.2 Processing steps (UI)

Step IDLabelWhat happens
readReading fileFile bytes/text loaded in the browser
extractExtracting recordsCSV or PDF parser produces raw row objects
detectDetecting CDC operationsSF_OP / aliases mapped to insert/update/delete
mapMapping fieldsnormalizeRawRow builds structured CDCRecords
insightsGenerating insightsanalyzeRecords builds stats, lifecycles, QA, charts
dashboardPreparing dashboardNavigate to dashboard with full AnalysisResult

3.3 Architectural principles

  • Client-only analysis — no server round-trip for CDC content
  • Evidence-first UI — every insight/timeline step carries evidence strings and an evidence category
  • Offset-aware chronology — prefer SF_OFFSET_ID over timestamps when ordering events
  • Human / raw dual view — same data, two presentation modes
  • OpenSooq brand fidelity — official palette (blue #33529D, green #87BE57)

8. Data Pipeline

8.1 CSV parser (lib/parser/csv.ts)

  • Library: Papa Parse
  • Requires a header row; empty lines skipped
  • APIs: parseCsvText, parseCsvFile
  • Throws NO_CDC_DATA when no usable rows are found

8.2 PDF parser (lib/pdf/parse-pdf.ts)

Uses pdfjs-dist with a local worker. Pages are extracted via getTextContent, then laid out by Y-baseline grouping.

Extraction strategies (in order):

  1. Log history admin table (parseLogHistory)
  2. Delimited tables (headers with CDC hints such as SF_OP, SF_TIMESTAMP)
  3. Key-value blocks (FIELD: value / FIELD = value)
  4. Inline JSON objects with ≥3 keys
Scanned PDFs If extracted text is shorter than ~40 characters × page count, the file is flagged scannedLikely and processing throws SCANNED_PDF. Image-only scans are not supported.

8.3 Log history (lib/pdf/log-history.ts)

Expected columns: Name | Is Moderator | Action | Action On | Diff | Date.

  • Detects listing ID from /post/{id} URLs or labelled IDs
  • Normalizes timestamps (ISO, DMY, YMD)
  • Maps action text to status definitions; unresolved rows produce warnings
  • Emits synthetic CDC rows with SOURCE: LOG_HISTORY, merged with table records

8.4 Normalization (lib/normalization/normalize.ts)

recordsFromRows → normalizeRawRow for each non-empty row:

  1. Uppercase keys via normalizeKey()
  2. Resolve aliases (e.g. ID / LISTING_ID / POST_ID; SF_OP / OPERATION)
  3. Parse LAST_EDIT_ACTION JSON when present
  4. Build nested CDCRecord (entity / status / user / cdc / raw)
  5. Assign uid: {id}-row-{index}-{requestId|index}

Operation mapping: insert (i, create), update (u, updated), delete (d, deleted), else unknown.

Timestamp priority: SF_TIMESTAMP → TIMESTAMP → RECORD_UPDATE_DATE → DATE → RECORD_INSERT_DATE.

8.5 Chronological ordering (ordering.ts)

CDC dumps are often newest-first and timestamps may share second precision. Sort priority:

  1. SF_OFFSET_ID / SF_OFFSET / OFFSET_ID / LAST_EVENT_ID (ascending)
  2. SF_TIMESTAMP (ascending)
  3. Original file index as tie-break

11. Insights, Lifecycle & QA

11.1 Analysis orchestrator

analyzeRecords in lib/insights/engine.ts runs:

  1. computeStats — operation / violation / active counts
  2. buildLifecycles — per-listing journeys
  3. buildGlobalTimeline — flat sorted steps
  4. buildStatusTracker — status history
  5. buildSmartInsights — activity mix, violations, top country, peak hour
  6. buildQaInsights — anomaly rules
  7. detectImportantEvents — rule actions, violations, deletes (cap 100)
  8. buildTimeline — flat CDC events
  9. detectChanges — first-vs-last field diffs (cap 200 groups)
  10. buildCharts — operations, status, country, language, overTime, violationsOverTime, activityByHour
  11. Warnings for unrecognized status codes

11.2 Lifecycle

Listings are grouped by ID, sorted chronologically, and consecutive pairs are diffed across 18 tracked fields (title, description, price, status, active, featured, violation, category, city, country, language, hasPrice, repost count, expiration, etc.).

Each step has a StepKind: created, activated, deactivated, updated, price, status, violation, rule, featured, category, reposted, expired, deleted, or event.

11.3 Status tracker

  • Groups by listing ID, else title+member, else row index
  • Builds StatusPoint[] and StatusTransition[]
  • Aggregates buckets with current / ever / record counts
  • MULTI_CHANGE_THRESHOLD = 3 drives warning severity
  • Potential issues: active + problem status; featured + inactive

11.4 Evidence categories

CategoryMeaning

POTENTIAL_ISSUEQA anomaly — not labelled as a confirmed bug

14. Privacy & Security

Default posture Uploaded files are read with browser File APIs and analyzed in memory. Nothing is uploaded to OpenSooq servers or third-party AI services as part of the analysis flow.
  • Sensitive fields (member ID, email, phone) masked unless the user toggles reveal
  • Error IDs are generated locally for support correlation only
  • No environment secrets are required for core functionality
  • Suitable for handling internal CDC exports on a locked-down workstation
Operational note Revealing sensitive data on a shared screen still exposes PII. Prefer keeping masking on during demos and screen shares.

18. Troubleshooting

SymptomLikely causeWhat to try
Error SCANNED_PDF Image-only / OCR-less PDF Export a text-based PDF or use CSV instead
Error NO_CDC_DATA Empty file or no header/rows Confirm delimiter and header row; try sample CSV
Events appear out of order Missing SF_OFFSET_ID; colliding timestamps Include offset IDs in the export; verify sort priority
Unknown status labels Nonstandard status text Add alias in listing-statuses.ts or use numeric codes
Sensitive values visible Reveal toggle enabled Turn off “Show sensitive” in the header
Large file feels slow Browser memory / CPU bound Filter the export upstream; process fewer pages/rows
PDF tables incomplete Complex layout / multi-column gaps Prefer CSV; or ensure tab/pipe-delimited text layout
